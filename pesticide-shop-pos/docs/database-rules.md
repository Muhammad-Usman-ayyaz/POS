# Database rules and service flows

The schema is in `packages/db-sqlite/migrations/001_init.sql`, plus later numbered migrations (`002_invoice_payment_method.sql` adds `invoices.payment_method`; `003_user_recovery_code.sql` adds `users.recovery_code_hash`; `004_product_groups.sql` adds product groups and pack sizes; `005_return_tax_and_name_snapshot.sql` adds the invoice line names, `tax_refund` and the low-stock rule; `006_sale_request_id_and_held_bills.sql` adds `invoices.request_id` and `held_bills`). Never edit an applied migration. The database refuses many bad writes by itself (negative stock, selling expired batches, over-returns, editing history). The services below create the rows. The database does NOT create stock or ledger rows automatically.

## Units and money
- `products.base_unit` is ml, g or piece. `pack_size` is base units per pack (1L bottle = 1000 ml).
- Quantities (`qty`, `qty_delta`, `min_stock`) are integers in the base unit.
- Prices (`retail_price`, `wholesale_price`, `unit_price`, `cost_price`) are paisa per pack. **Selling prices (retail, wholesale, `unit_price`) include tax.** Tax is never added on top.
- `line_total = ROUND(qty * unit_price / pack_size) - line_discount`. Round once per line. This is what the customer pays for the line, tax included.
- `tax_amount = ROUND(line_total * tax_rate_bp / (10000 + tax_rate_bp))`: the tax that is inside `line_total`, taken out of the discounted line. Rounded once, halves up. A line of Rs 1,180 at 18 percent has Rs 180 tax and Rs 1,000 without it.
- `invoices.subtotal = SUM(line_total - tax_amount)`, `tax_total = SUM(tax_amount)`, `total = subtotal + tax_total`, which is exactly `SUM(line_total)`. The view `v_invoice_mismatch` (total against the sum of the lines) must stay empty. Each line's tax is rounded on its own and the invoice only adds them up, so rounding can never make the two differ. The line without tax is `line_total - tax_amount`, never rounded separately.
- A cart line over two batches is two `invoice_items` rows. The discount is shared between them by price, and each row has its own `line_total` and `tax_amount`.
- `tax_rate_bp` is basis points. 1800 means 18 percent. It is set per product and copied onto each invoice line.
- `v_profit_by_day` counts revenue as `line_total - tax_amount` (the sale without its tax) and takes the matching share off for returns. It needed no change when prices became tax-inclusive.
- Migration 001's header comment still shows the old formula (`... + tax_amount`). It is a comment only: no table, constraint or view depends on it, and an applied migration is never edited. This file is the rule.
- Products with `allow_loose = 0` can only be sold in whole packs.

## Products: groups and pack sizes (migration 004)
A shopkeeper's "product" (Insecticide X) is a **product group**. Each pack size of it (250 ml, 500 ml, 1 L) is a row in `products`, so batches, stock movements, invoice lines and every foreign key work on SIZES exactly as before. Every size keeps its own stock, batches, prices, tax rate, barcode, SKU and `min_stock`, because sealed bottles of different sizes are different physical stock. There is no conversion between sizes.
- `product_groups`: `name_en`, `name_ur`, `category_id`, `brand_id`, `notes`, `is_active`, and the usual editable columns (`version`, `updated_at`, `deleted_at`, change_log triggers, no hard delete). The group is the **source of truth** for names, category and brand.
- `products.group_id` (which group) and `products.pack_label` ("500 ml"). The label may be empty only while the group has a single size; once a group has two or more live sizes every size needs a label, and labels are unique within the group.
- **Denormalized copies.** `products.name_en`, `name_ur`, `category_id` and `brand_id` are copies of the group's values, kept so invoices, error messages and views that read `products.name_*` keep working: `name = group name` when the label is empty, otherwise `group name || ' ' || pack_label`, in each language; `category_id` and `brand_id` equal the group's. Only the catalogue service writes them, in the same transaction that changes the group or the label. `v_product_group_mismatch` lists any size where a copy has drifted and must stay empty.
- **`group_id` is never NULL, but the column is declared nullable.** SQLite cannot add a NOT NULL foreign-key column to an existing table, and rebuilding `products` (which every other table references) needs foreign keys switched off outside the migration transaction. Two triggers (`trg_products_group_id_required_ins` and `_upd`) refuse a NULL on insert and on update instead. The Zod `Product.group_id` is strict, and `packages/db-sqlite/tests/schemas-match-db.test.ts` names this as its one exception (and checks that both triggers exist and work).
- Rules the database enforces (the service checks the same ones first, to give a clear error): sizes of one group share a `base_unit` (so group stock can be added up); labels are unique per group among live sizes; a size cannot be active inside an inactive group, or live inside a deleted one; a group with active sizes cannot be deactivated and one with live sizes cannot be deleted. Barcodes and SKUs are unique across all sizes ever made.
- **Backfill.** The migration gives every existing product its own group (a fresh UUID) with the product's names, category, brand, `is_active` and `deleted_at`, and `pack_label = ''`, so no name changes. Joining separate products into one is done with the `moveSize` service.
- **Audit.** Every change to the catalogue is in `audit_log`, in the same transaction as the change: `price_changed`, `tax_rate_changed`, `size_changed`, `size_activated` / `size_deactivated`, `group_changed`, `group_deactivated` / `group_reactivated`, `size_moved`. Creating a product or a size is not a change and has no row. Field changes list the field names with the old and new values; nothing is written when no field really changed.
- **Services** (`createCatalogueService`, owner only): `createGroup` (with optional first sizes), `updateGroup` (rewrites every size's copies), `addSize` (if the group's only size has an empty label, `existing_size_label` labels it in the same transaction), `updateSize`, `setSizeActive`, `setGroupActive` (deactivating switches off every size; reactivating switches on only the group), `moveSize` (same unit, unique label, names rewritten, an emptied source group is switched off, one audit row) and `search`. A size that has batches keeps its pack size and unit.
- **Search** is done in core, the same on every backend: both languages, lower case, Eastern Arabic (٠-٩) and Urdu (۰-۹) digits read as 0-9, Arabic and Urdu letter variants (ي ى to ی, ك to ک, ه ة ۃ to ہ) read as one, diacritics and joiners dropped, "500 ml" the same as "500ml". Every word typed must match. A barcode or SKU matches only when typed or scanned in full.
- **Search speed (measured with 5,000 products x 3 sizes, 30,000 batches, 30,000 stock movements, on the development PC).** The first version took 5 to 22 seconds per search (it re-normalised every name on every call and regrouped sizes with a quadratic loop). Now: the searchable text (names, labels, structure) is built once into an index (`buildCatalogueIndex`) and reused until a product or a product group changes; the repository's `catalogueSignature()` (one count and one sum of `version` per table, cheap, and it does not move when stock moves) tells the service when to rebuild. **Stock is not in the index:** it is looked up for just the sizes on the page being returned (`stockOfSizes`, one statement per 500 sizes), so a sale or a receipt never makes the next search slow. A screen asks for one page (`searchPage` with `limit` and `offset`, at most 1,000 products) and gets `total` back; the screen waits 150 ms after the last keystroke before searching and ignores any reply that is not for the latest text (`packages/ui/src/lib/use-debounced-search.ts`). Results: a search takes 7 to 19 ms, including the first one after a sale; the first search after a product or group is edited rebuilds the index and takes about 200 to 250 ms, once per edit.
- **The Products screen's data** (`catalogue.list`). Each size comes with its stock picture, worked out from its batches and movements (nothing stored): `stock_total`, `stock_sellable`, `expired_stock`, `next_expiry` (soonest batch that still has stock, expired ones included), `next_sellable_expiry`, `batch_count` (every live batch, empty or not: any batch locks the pack size) and `stocked_batch_count`. Three flags use the same rules as the database views: **low** = the size has a minimum (`min_stock` above 0), sellable stock is at or under it, and the size is switched on. A size with minimum 0 has no alert set and is never low, even with no stock. `v_low_stock` and `v_group_stock.low_size_count` use the same rule (migration 005), and a test checks that the views and the screen list exactly the same sizes; **near expiry** = the soonest unexpired batch with stock expires today or within `near_expiry_days` (30 by default, `v_near_expiry`); **expired** = stock still sits in an expired batch (`v_expired_stock`). A test checks the three flags against the three views. The filter chips count products, and SIZES that are low, near expiry or expired, over the whole active catalogue whatever was typed. Each product also gets a summary (size count, the unit its sizes share, total stock in that unit, the lowest and highest retail and wholesale price per pack). **Cost is owner-only:** `cost_price` (the cost of the batch that sells first: earliest unexpired batch with stock) is added to a size only when `include_cost` is asked for, and is otherwise absent from the answer, not even a null; the main process only passes it for the owner. The stock picture of all sizes is cached until the next write of any kind (`changeToken`) or the next day. Measured with 5,000 products x 3 sizes (30,000 batches and movements), one page of 50 products: a repeat call takes 16 to 37 ms; the first call after a sale takes about 190 ms (the stock picture is rebuilt, in one pass over the batches and movements); the first call after a product or group edit takes about 400 ms (the text index is rebuilt too). Screens should therefore load the list once and filter and page from it with `list`, not call it per keystroke without the typing delay.
- **Receiving stock and batch numbers.** A batch number belongs to ONE size (the same number on another size is fine). Reusing it for the same size with a different expiry or cost is refused as `BATCH_CONFLICT`, whose params say what clashed (`kind`, `batchNo`, `existingExpiry`, `newExpiry`, `existingCost`, `newCost`). `kind` is `expiry` when only the expiry differs (the screen may offer "use the existing expiry" or "save as a new batch number") and `cost` when the cost differs, whatever the expiry (only "save as a new batch number": cost history is never rewritten). A purchase can pay the whole total at once with `pay_in_full` (the total is worked out after the discount); do not also give `paid_amount`.
- **Suppliers, categories and brands** are small lists chosen from in forms. The owner quick-adds one (`createReferenceService`); a name already in the list (same language, ignoring case, spacing and Arabic/Urdu letter variants) is refused as `DUPLICATE_NAME`. Anyone signed in may read the lists.
- **The name on an invoice line** (migration 005). Every `invoice_items` row has `name_en` and `name_ur`: the display name of the size (group name plus size label) AS IT WAS WHEN IT WAS SOLD. The sale service copies them from the product itself; the renderer and the contract cannot send a name (`name_en` or `name_ur` on a sale or a line is refused as `INVALID_INPUT`). At least one of the two is set (a trigger refuses a new line with neither). The line is append-only, so the name never changes; a later rename of the product changes the next sale and nothing already sold. Receipts and reprints (Phase 5) read these columns, never `products`. Lines that existed before migration 005 were given the product's name AS OF THE MIGRATION (the name at sale time was never stored), so a product renamed before then shows its new name on old lines.

## Ledger sign
Positive `amount_delta` means the customer owes more (or we owe the supplier more). Payments and returns are negative.

## Record a sale (one transaction)
1. Take the next invoice number for this device from `number_sequences` (format like `INV-A-000123`).
2. Insert `invoices`, with `payment_method` (cash, bank, easypaisa or jazzcash, default cash) for the amount paid at sale. Credit sales need a customer. A walk-in sale must be paid in full. The unit price of each line is looked up from the product (`retail_price` or `wholesale_price` by the invoice's price type); the cashier cannot type a price. A different price is an owner-approved `price_override` on that line, and the approval is written to `audit_log`.
   A credit sale (a customer, with something unpaid) is refused if the customer's balance plus the unpaid amount would pass `customers.credit_limit`. A limit of 0 means no limit is set, so nothing is checked. The balance includes the opening balance. An owner can approve a sale over the limit with a `credit_override`, which is written to `audit_log`.
3. For each line, choose batch(es) earliest-expiry-first, skipping expired batches. One `invoice_items` row per batch used. Copy the batch `cost_price` onto the line, and the product's `name_en` and `name_ur` as they are now.
4. Insert a `stock_movements` row (`sale`, negative qty) per invoice item.
5. If there is a customer: insert `ledger_entries` (`invoice`, plus total). If money was paid now, insert `payments` (`in`, with the same method as `invoices.payment_method`) and a `ledger_entries` row (`payment`, minus amount).
6. Walk-in money lives on `invoices.paid_amount` and `invoices.payment_method` only. `payments` and `ledger_entries` need a real customer or supplier.
7. Cash received report = `payments` (in, cash) + walk-in `invoices.paid_amount` where `payment_method` is cash. Do not add `paid_amount` of customer invoices: that money is already in `payments`.

## Record a customer payment
`payment.receiveFromCustomer`, ONE unit of work (`deps.uow.run`):
1. The amount is a whole number of paisa above zero. The payment is dated now: there is no back-dating, and the input has no date.
2. Bank, Easypaisa and JazzCash need a `reference_no` (blank counts as missing: `REFERENCE_REQUIRED`); cash does not. An optional `note` (at most 200 characters).
3. **Advance.** If the amount is more than the customer's balance now (a customer who owes nothing, or is already in credit, included), the payment makes them a customer in credit. It is refused with `ADVANCE_NOT_CONFIRMED` unless `confirm_advance: true` is sent. Paying exactly the balance needs no confirmation.
4. Take the receipt number with `numbers.next('payment')` INSIDE the unit of work (`RCP-<branch>-000001`), insert `payments` (`in`, with `receipt_no` and `note`) and `ledger_entries` (`payment`, minus amount). If anything fails, the payment, the ledger row and the receipt number all go back; a refused payment never uses a number.
5. The result is `{ payment, receipt_no, balance_after, advance }` (`advance` is true when `balance_after` is below zero). Payments reduce the overall balance, not one invoice.
6. No audit row: `payments` (append-only, with who and when) is the record of a payment. A payment taken at the counter together with a sale is part of the sale: it has no payment receipt number (its `receipt_no` stays NULL).
Supplier payments (`payToSupplier`) are unchanged.

## Customer statement
`khata.statement({ customer_id, from?, to? })` (read only):
- Rows are the customer's ledger rows (`party_type = 'customer'` always) ordered by `(entry_date, rowid)`, each with the balance after it. Each line also carries what to print beside it: a label (`opening`, `sale`, `payment`, `return`, `adjustment`), the invoice number (sale rows), the return number (return rows), and for payment rows the method, reference, receipt number and note. The joins only add columns: they never add or drop a row.
- `from` and `to` are whole UTC days, both included. With `from`, the first line is a **brought-forward** line equal to the sum of every ledger row before that day. `totals` are `owes_more` (the plus rows in the range) and `owes_less` (the minus rows in the range, as a positive number).
- `closing_balance` is always the sum of every ledger row up to and including `to` (brought forward + owes_more - owes_less). Without a `to` the service also compares it with `ledger.balance` and refuses to answer if they ever differ, so a statement can never disagree with `v_customer_balance`. Return and adjustment rows count like any other.
- Nothing is stored for a statement.

## Return (customer brings goods back)
1. Owner approves. A return must link to an active invoice.
2. Insert `sales_returns` and `sales_return_items`, each pointing at the exact `invoice_items` row. Quantity may not exceed `v_invoice_item_returnable.qty_returnable`.
3. Refund amount comes from the original line price, not today's price. Discounts return proportionally. The tax inside the refund is worked out the same running-difference way and stored on the line as `sales_return_items.tax_refund` (migration 005); over all the returns of one line it adds up to exactly the tax charged and never more (a trigger caps it per line). One return line's `tax_refund` can be a paisa more than its own `refund_amount` (the two round separately: a line of 3 units with a total of 2 and tax 1 refunds 1, 0, 1 and its tax 0, 1, 0), so the cap is on the line's total, not on each row.
4. Resellable items: insert `stock_movements` (`sale_return`, plus qty) on the same batch. Damaged or expired items do not go back into sellable stock.
5. Khata credit refund: insert `ledger_entries` (`return`, minus refund).
6. Cash refund and voiding an invoice: ledger and payment entries for these must be designed with the owner before coding. Void is a status change plus reversing rows. Never delete the invoice.

## Purchase (stock in)
1. Create or pick the `batches` row (batch number, expiry, cost price).
2. Insert `purchases` and `purchase_items`.
3. Insert `stock_movements` (`purchase`, plus qty) per batch.
4. If supplier credit is tracked: `ledger_entries` for the supplier (`purchase`, plus total) and `payments` (`out`) with a ledger row (`payment`, minus amount).

## Opening data
- Opening customer balance: one `ledger_entries` row, `entry_type = 'opening'`.
- Opening stock: one `stock_movements` row, `movement_type = 'opening'`, per batch.

## Reports from views
`v_batch_stock`, `v_product_stock` (one row per SIZE: total and sellable stock, with its group and label), `v_low_stock` (per size: switched on, `min_stock` above 0, and sellable stock at or under it), `v_group_stock` (a whole product: its sizes added up, size count, how many sizes are low by the same rule), `v_product_group_mismatch` (must stay empty), `v_near_expiry` (uses `settings.near_expiry_days`, default 30), `v_expired_stock`, `v_customer_balance`, `v_supplier_balance`, `v_invoice_item_returnable`, `v_profit_by_day` (a return takes back its refund minus `tax_refund`: the tax was never revenue; the total equals the rows to the paisa).
Overdue invoices are not a view yet: since payments hit the overall balance, treat payments as paying the oldest invoices first and calculate overdue in the service.
**This allocation is a DISPLAY rule only.** No payment-to-invoice allocation is stored anywhere, and nothing here changes a balance. `debtPicture` (khata service) treats all money received as paying the oldest debts first; from the invoices still open it gives the overdue list (past due date), `next_due` (the due date of the oldest unpaid invoice that has one; an opening balance has no due date and is never overdue) and, for the customers list, `overdue_amount` and `overdue_days` (the largest days overdue).

## First launch
The app must create the `shops`, `branches` and `devices` rows, the owner user, and default `settings` (for example `near_expiry_days = 30`) because every other table references them.

## Audit log
`audit_log` is append-only. Rows are written in the same transaction as the change they record, and the user is always the one signed in (taken from the session, never from the screen):

| action | when | user_id |
|---|---|---|
| `login` / `login_failed` | every sign-in; failed ones say why (`unknown_user`, `wrong_password`, `inactive_user`) | the user, or NULL for an unknown name |
| `price_override` / `credit_limit_override` | an owner approved a different price or a sale over the credit limit | the owner |
| `return_approved` | an approved sales return | the owner |
| `price_changed` / `tax_rate_changed` | a size's retail or wholesale price, or its tax rate, was changed (before and after are in `details`) | the owner |
| `size_changed` | a size's label, SKU, barcode, minimum stock, pack size, unit or loose-selling flag changed, or its label was set because another size joined (`details`: `fields`, and `before` and `after` with the old and new value of each changed field) | the owner |
| `size_activated` / `size_deactivated` | one size switched on or off on its own (`before` and `after` of `is_active`; a whole-product switch-off is `group_deactivated`) | the owner |
| `group_changed` | a product's English or Urdu name, category, brand or notes changed (`fields`, `before`, `after`; a rename is `name_en` and/or `name_ur`). The sizes' copied names follow and get no rows of their own | the owner |
| `group_deactivated` / `group_reactivated` | a product was switched off (with the sizes it switched off) or on | the owner |
| `size_moved` | a size was moved to another product (both groups, both labels, whether the old product was switched off) | the owner |
| `receipt_backdated` | a purchase was recorded with a receipt date other than today (yesterday's delivery entered today). A date after today is refused with `FUTURE_DATE`. A date more than 30 days ago (`OLD_RECEIPT_DAYS`) is refused with `RECEIPT_DATE_OLD` (with `days`) until the caller sends `confirm_old_date: true`; there is no hard limit. `details`: `purchase_date`, `entered_on`, `supplier_id`, `total`, and for a confirmed old one `days_ago` and `confirmed_by_user`. "Today" is the UTC date, like every other date in core | the user who recorded it |
| `invoice_printed` | an invoice was printed or saved as a PDF (`table_name` `invoices`, `row_id` the invoice; `details`: `kind` receipt or A4 invoice, and how it came out). The count of these rows is what makes the next print say COPY | the user who printed |
| `print_config_changed` | the owner changed a print or shop-document setting. ONE row per setting whose value really changed (a value sent unchanged writes nothing, and a save that changes nothing writes no row); `table_name` `settings` (`shops`, `row_id` the shop, for the shop name); `details`: `field`, `from`, `to` (null: not set). Written in the same transaction as the settings | the owner |
| `approval_used` | a one-use owner approval was spent on a sale (`table_name` `invoices`, `row_id` the invoice; `details`: `requested_by`, `actions`). Written by the sale service inside the sale's own transaction, so the invoice and this row exist together or not at all | the approving owner |
| `bill_held` | a cashier put a bill on hold (`table_name` `held_bills`, `row_id` the held bill; `details`: line count, customer). Written in the same transaction as the held row. The cart holds product ids, quantities, batch, discount as entered and the customer: never a price | the user who held it |
| `bill_resumed` | a held bill was taken back to the counter (one use: the same UPDATE that marks it resumed; a second try gets HELD_BILL_GONE). Same transaction | the user who resumed it |
| `bill_discarded` | a held bill was thrown away (one use, as above). Same transaction | the user who discarded it |
| `stock_adjustment` / `stock_write_off` | a stock count correction or a write-off | who did it |
| `owner_password_reset` / `owner_password_reset_failed` / `recovery_code_regenerated` | owner recovery | the owner, or NULL |

Passwords and recovery codes are never written to the log.

## Users and the recovery code
`users.password_hash` and `users.recovery_code_hash` are argon2id hashes made in the main process. The core services never see them: `UserRepository` leaves them out. The owner's recovery code is made at first launch, shown once, and replaced each time it is used or regenerated.

## Sync support
Triggers write `change_log` on every insert and update. Set `synced_at` after a successful sync. Unsynced rows cannot be deleted.

**Must be done before sync is built: a stable ledger sequence.** The "balance as of that sale" on a receipt (`balanceAsOfSale`) takes the ledger rows that come before the invoice's own entry, and today "before" means a smaller SQLite `rowid`. `rowid` is only the order of insertion on this one PC. When rows can arrive from another device they could land between local ones and change an old receipt's balance. So, before sync, a new migration must add an explicit monotonic sequence column to `ledger_entries` (filled for the existing rows in `rowid` order, assigned by the database or one writer, never by the screen), and `balanceAsOfSale` must order by it. Until then the function is correct for a single-PC shop only.

## Sale request id, held bills, quote and approvals (migration 006, Phase 5)
- `invoices.request_id` (nullable, 8 to 100 characters, unique when set, cannot change once set). `sale.create` first looks the id up: found means return that invoice (`replayed`), nothing written. Found with a different user, customer, amount paid or product quantities means `REQUEST_ID_REUSED`.
- `held_bills`: a saved cart (JSON `payload`, `line_count` > 0) with who held it, customer and price type. Status `held` then once `resumed` or `discarded` (with `resolved_by` and `resolved_at`). The cart cannot be edited and the row cannot be deleted (triggers). Not in `change_log`: it is a draft, not a business record. The `payload` holds only the cart's choices (product ids, quantity, batch id, discount as entered, optional note) and NEVER a price, tax, total or cost; `packages/db-sqlite/src/held-bills.ts` is the only code that writes it. Resume and discard are one UPDATE that only matches `status = 'held'` inside one transaction, so a bill can be resolved by exactly one caller (the other gets `HELD_BILL_GONE`).
- `sale.quote` uses the same planning as `sale.create` and writes nothing. It reports `issues` (stock, credit, payment, due date, approval) instead of throwing, and `discount_over_limit` per line (discount x 100 > gross x staff limit percent).
- Approvals and the wrong-password lock live in the main process (memory), not in the database. Audit rows: `approval_granted`, `approval_used`, `approval_failed`, `approval_locked`, `login_locked`, `discount_override`.

## Customers and Khata (migration 007, Phase 6)
- `payments.note` (nullable text typed when the payment is taken) and `payments.receipt_no` (nullable, like `RCP-A-000001`). `receipt_no` is written only when the payment row is inserted: `payments` stays append-only (the no-update and no-delete triggers are unchanged). A unique index (`uq_payments_receipt_no`, only where it is not NULL) keeps receipt numbers unique across the file, the same way `invoices.invoice_no` is unique (the branch code is inside the number, so each device and branch has its own range). Payments made before migration 007 keep a NULL receipt number: nothing was rewritten.
- Number sequence `payment`, prefix `RCP-<branch code>-`, taken with `numbers.next('payment')` in the same transaction as the payment. Migration 007 adds the row (from 0) for every device that already exists, copying the device's `invoice` prefix with `INV` changed to `RCP` (a device with no invoice sequence gets `RCP-<its branch code>-`); `firstLaunchSetup` adds it for new shops.
- `customers.father_name`, `cnic`, `phone2`, `guarantor`: optional nullable text, empty for every existing customer. The screens show them only when the setting `customers.show_farmer_fields` is on; the stored data stays when it is turned off.
- Settings `default_credit_limit` (paisa, default 0) and `customers.show_farmer_fields` (default off) have no row until the owner changes them: like `staff_max_discount_percent`, a missing row means the default in code. Owner-only to change.
- Nothing about how a balance, a payment or an opening balance is calculated changed in 007.

### Customers service (Phase 6 M1)
- `customers.create({ fields, created_by, privileged, confirm_duplicate? })`: anyone adds a customer with contact fields. The credit limit, price type and farmer fields are the owner's (`privileged`, checked against the user's real role): from anyone else they are REFUSED with `FIELD_NOT_ALLOWED`, never quietly dropped. A new customer starts with the shop setting `default_credit_limit` (code default 0) and the retail price type. Another live customer with the same normalised name (case, spaces, Urdu letter and digit variants, either language against either) or the same phone (digits only: spaces, dashes, a leading 0 or +92 ignored) needs `confirm_duplicate: true`, otherwise `DUPLICATE_CUSTOMER` (params `count` and `matches` as JSON text). Creating a customer is not audited (like creating a product).
- `customers.update({ customer_id, fields, expected_version, actor })`: contact fields only (name_en, name_ur, phone, village, notes; one name must remain). A credit limit, price type or farmer field is not accepted. A stale `expected_version` is `VERSION_CONFLICT` (params `expected_version`, `current_version`). Nothing is written when nothing changed.
- `customers.setTerms({ customer_id, credit_limit, default_price_type, father_name?, cnic?, phone2?, guarantor?, expected_version, actor })`: owner only. One audit row `customer_terms_changed` (`details`: `fields`, `before`, `after`, and `below_balance` + `balance` when flagged) in the same transaction as the change; no row when nothing changed. Setting a limit above 0 that is lower than what the customer owes is allowed and returned as `below_balance: true`.
- `customers.findDuplicates`, `customers.list` and `customers.get`: `credit_left` is the limit minus the balance, never below 0 (`over_limit: true` then); a limit of 0 is `no_limit: true` with `credit_left` NULL (never 0 or negative). List totals: `total_outstanding` is the sum of POSITIVE balances only, `overdue_total` the sum of overdue amounts (both shop-wide, not narrowed by the search or filter), `count` the rows matching the search and filter.
- `customers.search` also matches a typed phone number by digits only.
- `customerSettings.get` / `set`: `default_credit_limit` (non-negative whole paisa) and `customers.show_farmer_fields`. `set` is owner only and writes one `customer_setting_changed` audit row (`field`, `from`, `to`) per setting that really changed.
