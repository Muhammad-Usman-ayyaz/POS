# Decisions made

| Area | Decision | Effect |
|---|---|---|
| Platform | Offline desktop app, Electron + SQLite, no server | Free to run. Backups handled by the app |
| Units | Loose and sealed sales | Stock in base units with `pack_size` and `allow_loose` |
| Sales snapshots (migration 005) | An invoice line stores the size's display name (English and Urdu) as it was at sale time, copied by the sale service and never accepted from the screen; a return line stores the tax inside its refund; the low-stock views require a minimum above 0. Existing rows were backfilled: tax by the same running difference the service uses, names from the product's current name (with the limit that earlier renames cannot be recovered). Backfilled rows get `version` + 1, and a `change_log` update row only if their insert was already synced | Reprints cannot change when a product is renamed; profit matches refunds to the paisa; the Products screen and the database views agree on what is low |
| Pack sizes | One product with several pack sizes, for example Insecticide X in 250 ml, 500 ml and 1 L (owner's answer to question 1) | `product_groups` is the parent. Each size is still a `products` row with its own stock, batches, prices, tax rate, barcode and `min_stock`. Sizes of one product share a base unit and are told apart by `pack_label`. No conversion between sizes |
| Receive stock screen | Owner only. Clashes are found on the screen from `stock:batchesOf` and settled on the line; the shell's `BATCH_CONFLICT` stays the final word. Always paid in full, no draft. Packs are whole numbers (no half packs); the packs are multiplied by the size's pack size before sending. "Today" and the future-date check use the UTC date, like the shell (open question 16) | Cost history is never rewritten; a half pack would need a decision about loose receiving |
| Product form | Owner only (staff are redirected). The base unit belongs to the product and can change only while no saved size has batches and at most one size is saved. A saved size is never removed, only switched off. A locked pack size cannot be edited (read-only with a lock); pressing it or a `PACK_SIZE_LOCKED` reply explains and offers "Add a new size". Edits are sent as several calls (product, sizes, new sizes, switch on/off); a failure stops the rest and reloads the form | Atomic edits would need a new service that changes the product and all sizes in one transaction; not built yet. Tax is typed as a percentage and stored in basis points; prices are typed as tax-inclusive rupees |
| Receipt date | A past date is allowed (the owner may enter yesterday's delivery) and leaves an audit row `receipt_backdated`; more than 30 days ago the screen must ask "This receipt is dated N days ago. Save anyway?" (`RECEIPT_DATE_OLD`, then resend with `confirm_old_date`), no hard limit; a future date is refused (`FUTURE_DATE`). "Today" is the UTC date, so between midnight and 05:00 in Pakistan a receipt dated with the local date is wrongly refused as future (see open questions) | Entering a late delivery must be possible; a typo in the year must not silently succeed |
| Receiving stock | Owner only (open question 15). Supplier chosen or quick-added in the form; paid in full by default, payment fields hidden. Same batch number with a different expiry offers "use the existing expiry" or "save as a new batch number"; a different cost offers only a new batch number | Cost history is never rewritten. Staff never see cost |
| API permissions | Every API channel has a policy in `apps/desktop/src/main/permissions.ts` (public, signed-in, or a capability), enforced for every call by a guard around all handlers before any service runs; a test fails if a channel has none. The renderer never sends `actor_id`, `created_by`, `approved_by` or `user_id` (the schemas refuse them): the user comes from the session | Owner-only: catalogue changes, Receive stock, quick-add of suppliers, categories and brands. Lists are for any signed-in user |
| Cost visibility | Cost is owner-only everywhere: the catalogue list gets `cost_price` only when the signed-in user is the owner (the renderer cannot ask for it), a staff sale reply has no `cost_price` on its lines, and errors that carry a cost (`BATCH_CONFLICT`) are stripped of it for anyone else | **Rule: cost must never reach staff in any reply, data or error.** The deep-scan test in `apps/desktop/tests/catalogue-api.test.ts` (every channel, as staff, good and bad input, every reply scanned for any cost key or amount) is the guard for it: a new channel or field that carries cost must be caught there before it ships. It found the staff sale-reply leak (fixed in `ca8f3a1`) |
| Catalogue changes | Only the owner changes the catalogue (default, open question 14) | Every change to a product or a size (prices, tax rates, labels, SKU, barcode, minimum stock, pack size, unit, switching on or off, renaming, moving) is written to `audit_log` with the changed fields and their old and new values |
| Batches | Batch and expiry on all products | Every stock movement has a batch |
| Pricing | Retail and wholesale price | Two price columns. Invoice stores the price type used |
| Payments | Reduce the customer's overall balance | Payments go to the ledger, not to one invoice |
| Credit | Credit limit and due dates | `credit_limit` and `due_date` |
| Returns | Must link to an invoice. Owner approves | `sales_returns.invoice_id` required |
| Supplier returns | Case by case | Small `purchase_returns` tables |
| Users | Owner plus staff | Roles. Owner-only: approve returns, change prices, view profit and cost |
| Printing | Thermal 80mm and A4 | Two templates from one invoice model |
| Language | English and Urdu | `name_en`, `name_ur`, RTL, Urdu font, bilingual search |
| Volume | 20 to 50 invoices a day | SQLite needs no tuning |
| Opening balances | Entered by hand | One `opening` ledger row per customer |
| Stock | Out of stock is blocked | Check inside the sale transaction and trigger |
| Discounts | Per item only | `line_discount`. No invoice-level discount |
| Payment methods | Cash, bank, Easypaisa, JazzCash | Optional reference number |
| Batch choice | Automatic with manual override | Earliest expiry first |
| Tax | Sales tax on invoices | Rate per product, amount saved per line |
| Tax and prices | Selling prices already include tax (owner's answer to question 6) | `line_total` is the price less the discount and tax is never added on top. `tax_amount` is the tax inside `line_total`. `subtotal` is the total without tax, and `total` is the sum of the lines. A return refunds from `line_total` in proportion, so its tax comes back in proportion too |
| Near expiry | Warn at 30 days | `settings.near_expiry_days` |
| Migration | Start fresh, no Django import | Old version used as reference only |
| ORM | None. Plain SQL migrations and typed repositories | Triggers and views live in SQL |
| Desktop shell | Electron 42 pinned exactly; Electron build of SQLite pinned and verified | See `docs/native-sqlite.md` |
| Sign in | argon2id, session in the main process, owner and staff | Owner-only rules are checked in the main process |
| Recovery | One-time owner recovery code, shown once, stored as a hash | Resets the owner password; replaced after use |
| Staff limits | Stock changes and opening balances are owner-only by default | Open question 12 |
| Security | Strict Content-Security-Policy in the built app | Relaxed only for the Vite dev server |
| Audit | Sign-ins, overrides, returns, stock changes, resets are in `audit_log` | See `docs/database-rules.md` |
| Sale request id (Phase 5) | `invoices.request_id` is a unique column (migration 006). The same id again returns the invoice already made, even after a restart; the same id with a different cart, customer, amount or user is refused (`REQUEST_ID_REUSED`). A replay has `payment_id: null` | Prices are not compared on a replay (a price change between two clicks must not make a retry fail) |
| Quote (Phase 5) | `sale:quote` runs the same planning code as `sale:create` and writes nothing; problems come back as `issues` instead of errors. A test checks that quote and sale agree to the paisa over random carts | The screen shows the quote; it never does its own money arithmetic |
| Owner approval at the counter (Phase 5) | Staff need the owner for: going over the credit limit, a different price, a discount over the staff limit (setting `staff_max_discount_percent`, default 5). The owner types their own password; the shell gives a token that works once, for one minute, for exactly those actions, this cart and amount, and the person who asked. Any try with a token spends it. The token is held in memory and never written to the log | The owner is the approver of their own sales and needs no token. Payment method, reference and due date are not part of what is approved. Tokens do not survive a restart |
| Wrong-password lock (Phase 5) | Five wrong passwords lock that name (sign-in) or that requester (approval) for 30 seconds; each new lock doubles, up to 15 minutes; a right password clears the count; the password is not even checked while locked. In memory, so a restart clears it | Sign-in had no lock before Phase 5. Unknown names are locked the same way so nothing shows which names exist |
| Printing permissions (Phase 5, M5/M6) | Looking up invoices (`invoices:list`, `invoices:get`, `invoices:receipt`), printing (`print:document`), the printer list and reading the print settings are open to any signed-in user: the counter reprints receipts all day and none of it holds cost. Only `print:setConfig` (the printer, the receipt and invoice languages, the shop's Urdu name, address and phone) is owner-only (capability `print.configure`); changes are in `audit_log` (`print_config_changed`) | Not asked of the owner: the safe default, like open questions 12 and 14. To relax it, add `'staff'` to that one capability line |
| Receipt contents (Phase 5) | Names, size labels and tax come from the invoice line as sold (`invoice_items.name_en/name_ur`, `tax_amount`), never from today's product. The receipt shows the line before discount and one "Discount" line (as designed); the A4 invoice shows the discount and, added to the design, the tax on each line. The batch NUMBER is on the A4 invoice only (it is not cost). Walk-in sales have no customer, balance or Khata lines. A voided invoice prints VOIDED | `docs/design/80 mm receipts, English and Urdu.png` and `A4 invoice, English and Urdu.png` |
| Balance on a receipt (Phase 5) | "Your balance now" is the customer's balance right after THAT sale: the ledger before the invoice's own entry (by row order) plus what the sale put on Khata. A payment, return or sale made afterwards has later rows and never changes it | Computed on read from the append-only ledger; nothing is stored. Row order is `rowid`: when sync arrives, remote rows must not be inserted between local ones |
| COPY (Phase 5) | Every print or saved PDF writes an `invoice_printed` row to `audit_log` (user, kind, language, result). The second and later print of the SAME kind of document for an invoice says COPY (a receipt then an A4 invoice: the A4 is not a copy). Looking at a receipt on screen is not a print | No new table or migration: the audit log is already append-only. `invoices:receipt` says `is_copy` so the screen can warn before printing |
| Document fonts and bidi (Phase 5) | Each page carries its fonts as `data:` addresses (IBM Plex Sans 400/600/700 and the Arabic-script subset of Noto Naskh Arabic, bundled into the main process by Vite `?inline`); its Content-Security-Policy forbids every network request. Latin or digit runs inside Urdu text (a size label such as "1 L") are wrapped as left-to-right islands, or the bidi rules print "L 1". Date and time are shown in `Asia/Karachi` (setting `shop.time_zone`), with English month names and Latin digits in Urdu too, as in the designs | Nothing depends on the PC's fonts or the internet |
| Address and phone on documents (Phase 5) | Only the shop NAME is real. Address and phone come from the print settings (`shop.address`, `shop.phone`) and print as a clearly marked placeholder "[Address and phone]" (Urdu "[پتہ اور فون]") until the owner enters them. Never invented | Open question 18 |
| PDF fallback (Phase 5) | `print:document` with output "printer" prints; with no printer, a missing chosen printer, or a printer error it saves a PDF instead (Documents/Pesticide Club POS/Receipts, opened for the user) and the reply says `status: 'pdf_saved'` with `fallback` set to `no_printer` or `print_failed`. That is a normal reply, not an error. Only when not even a PDF can be made is it an error (`INTERNAL`) and nothing is recorded | The screen shows the fallback as a notice |
| Held bills (Phase 5) | `held_bills` (migration 006) is a local draft: not in `change_log`, cart fixed once saved, resolved once (resumed or discarded), never deleted | Visible to all cashiers. Now kept in the database through four channels, see "Held bills in the database" below |
| POS screen (Phase 5, M2-M4) | Totals and checks come from `sale:quote` only. One `request_id` per bill, kept for retries. Cash handed over beyond the bill is change (sale sent for the total, change shown once, never saved). The owner approves with their own username and password, once per try. Held bills are kept in the database (see "Held bills in the database") | The screen cannot disagree with the sale; a double click cannot bill twice |
| Receipts are real text (Phase 5, open question 19 DECIDED) | Receipts and invoices are printed as real text with the font embedded, not as a picture. A bitmap step (capture the hidden window, print the image) is added only if a real printer shows the Urdu letters unjoined or in the wrong order | Text stays sharp, searchable in the PDF and light to print. Still to be checked on his real 80 mm printer |
| Accepted as built (Phase 5) | These were built this way and are accepted until the owner says otherwise: (1) the A4 invoice has a tax column; (2) the "pay by" date on a Khata sale defaults to 30 days from today; (3) loose-size buttons move the quantity by 50 for a pack of 500 or more, 10 for 100 or more, else 1; (4) change is shown on the screen only and never saved; (5) the sidebar has an "Invoices" item; (6) staff cannot offer a different price on a line (owner only); (7) the owner types their username (and password) in the approval dialog; (8) `print:setConfig` is owner-only (capability `print.configure`); (9) the Urdu shop name is an optional setting (`shop.name_ur`) | Each is a small, easily changed rule: none changes the data |
| Invoice dates on screen (Phase 5, M7) | The invoice history and its detail show dates in ONE zone, the exported constant `SHOP_TIME_ZONE` ('Asia/Karachi') in `packages/ui/src/pages/invoices/time-zone.ts`. Every screen that formats an invoice date reads it; a test checks the list and the detail both do. It will come from the setting `shop.time_zone` later (the printed documents already read that setting, default `Asia/Karachi`, through `DEFAULT_TIME_ZONE`) | One place to change, and no two screens can disagree |
| Balance on a receipt needs a ledger sequence (BEFORE SYNC) | `balanceAsOfSale` orders ledger rows by SQLite `rowid`. That is only safe while one PC writes them. Before sync is built, `ledger_entries` MUST get a stable, explicit, monotonic sequence column (added by a new migration, never by editing an old one; filled for existing rows in `rowid` order) and the balance must order by it. Rows that arrive from another device must not be able to slip between local ones | Not done yet. Without it a synced ledger could print a different "balance now" on a reprint |
| No ambiguous dates (typed dates) | Every date the person types or reads is `12 Oct 2026` in both languages; the shared `DateField` is a text box with a calendar button and reads typed text strictly: `12 Oct 2026`, `12-Oct-2026` and ISO `2026-10-12` are accepted, numeric day/month forms such as `05/10/2026` are refused with "Write the date like 12 Oct 2026" (never guessed, because the shop reads day first and the browser month first), impossible dates and years outside 2000-2100 are refused, nothing rolls over. The API still gets `YYYY-MM-DD`. Receive stock uses it for the date received and every expiry. Urdu month names stay open question 17. | A wrong guess would put a wrong expiry or receipt date into the stock records. |
| Held bills in the database (Phase 5) | Held bills are no longer in the browser's storage. Four channels: `bills:hold`, `bills:list`, `bills:resume`, `bills:discard`. Any signed-in user, owner or staff, may use all four (one counter, two people); staff may resume a bill the owner held and the other way round. The list shows WHO held each bill (the user's name, read from the users table by the id saved with the bill) and when. The holder is always the signed-in session user: the schemas are strict and have no `held_by`, `actor_id` or `user_id`. Resume and discard each run in ONE transaction as an UPDATE that only matches a bill still `held`; of two calls for the same bill exactly one changes a row, and the other gets `HELD_BILL_GONE` (also for an id that does not exist). Resume returns the cart with product names and pack data, and the customer's names; every step writes an audit row (`bill_held`, `bill_resumed`, `bill_discarded`). Old bills in a browser's localStorage are ignored (not imported, not deleted by the code): the shop had only demo data | Staff can see all held bills because they share the counter; a held bill holds no price or cost |
| NO PRICES in a held bill (Phase 5) | The database stores only what the cashier CHOSE: product (size) ids, quantity in base units, a batch id if one was picked by hand, the line discount as entered (`{ kind: 'amount', value: paisa }`), the customer id, the price type and an optional note. No unit price, tax, total or cost: the schema refuses them and a test looks at the stored row. The discount is an amount because the line dialog turns a typed percent into paisa when it is applied, so `kind` can only be `'amount'` today; the field is there so a percent could be added later | Prices change; a held bill is re-quoted with `sale:quote` on resume |
| Resume warnings without stored prices (Phase 5) | DECISION: "Price changed" and "Batch changed" need the price and batch the cashier saw, and those are NOT stored. They are remembered in the window's MEMORY only (`held-bills.ts`, a Map keyed by the held bill's id, filled when the bill is held in this run of the app and forgotten when it is resumed or discarded). A bill held in an earlier run of the app (or one whose memory was lost) is resumed WITHOUT those two warnings. "Removed" (a line that cannot be sold: no stock, product switched off, hand-picked batch gone) is still reported always, because the new `sale:quote` says it by itself | The alternative (storing the seen price) was refused on purpose: a stored price is a lie the day it changes. The cost: after a restart a price change on a held bill is not announced, but the screen still shows the new price on the bill and the total is the quote's. On resume the bill is shown at once and the check runs after, so a failed check never loses a bill that has already left the list |
| Print format, receipt footer, shop name (owner-only settings) | `print_format` (`80mm` default, or `a4`) decides which paper the plain Print button prints (counter and history); the explicit A4 and Save PDF buttons stay. `receipt_footer` (max 200, empty by default) REPLACES the design's fixed thank-you line on both papers only when it is not empty, and is printed as escaped text. The shop name is edited through `print:setConfig` (`shop_name`; there was no other channel) and written to the `shops` row that setup made, so the sidebar, login and documents all read the same name. All three are owner-only (`print.configure`); staff read them with `print:getConfig`. `setPrintConfig` compares with the stored value and writes and audits only keys that really changed: one `print_config_changed` row per key with `field`, `from`, `to`, in the same transaction; no change, no row | `shops` has no update trigger, so a rename does not bump `version` or reach `change_log`: before sync a new migration must add one (open item). Urdu strings marked for review in `docs/urdu-review.md` |
| The owner's approval is spent before the sale (accepted for now) | The one-use approval token is consumed when the sale is sent, before it runs. If the sale then fails (stock, a rule, a database error), the approval is burnt and the owner approves again | A safe failure: a wasted approval is better than an approval that could be used twice. A cleaner rule (spend it only when the sale commits) needs the approval check inside the sale's unit of work: revisit after the shop trial | Accepted for Phase 5 |
| Real-printer test is NOT done | Printing was tried only through Electron's printToPDF and the 'Microsoft Print to PDF' / an ordinary printer path, never on the shop's 80 mm thermal printer. Urdu is printed as real text (question 19): if it comes out unjoined on that printer, the fix is a bitmap step | MUST happen at the shop trial, on the real thermal printer, English and Urdu, receipt and A4, before go-live | Open until the trial |
| The Invoices screen has no design file | Built from the Products screen patterns and the POS tokens; the 'Invoices' nav item is an eighth sidebar item that the approved designs do not show | The owner will design it and update the sidebar; until then it is a working default, not an approved design | Open |
